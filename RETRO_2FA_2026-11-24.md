## 2. Root causes

### 2.1 IBKR Mobile and the gateway share one username (new, the main driver now)
IBKR allows **one brokerage session per username**. Opening IBKR Mobile with the same username
starts a second session. The gateway gets `Existing session detected`, and IBC is configured
`ExistingSessionDetectedAction=primary` (`config.ini:329`), so it reconnects at once and the phone
is thrown out — that is the "kicked out within 1 minute" on the phone.
**And the competing logins void the gateway's restart token**: four competing sessions between
22:58 and 05:34 → the 05:45 token was rejected → a new YubiKey touch.
This is hypothesis H1 of the first retro, now observed directly. The only earlier
`Existing session detected` in the surviving IBC logs is Nov 3 00:20 → **Nov 3 20:30 token
rejected**. IBC logs before Nov 21 are only snapshots at launches, so other mobile logins may be
missing; if you opened IBKR Mobile on most days, this likely explains most of the 5 "unexplained"
rejections (Nov 2, 3, 5, 6, 20).

### 2.2 The YubiKey was not plugged in at the weekly touch (25 h lost)
The reminder at 20:25 said "Key in a port directly on the PC" but did **not check** whether it was.
The login script did check (`ibkr-live-login.ps1:133`, `VID_1050` present) and stopped correctly,
but then:
- the watchdog kept **re-launching a login every hour** that could not possibly work (no key),
- each relaunch sent **two** critical pages (down + login), all night, until the cap was spent;
- nothing watched for the key being inserted, so even after plugging it in the user had to
  start the login by hand (21:19).

### 2.3 Night prompts nobody can answer
The 05:45 restart is after the US close, so a rejected token now prompts at 05:47 while the user
sleeps (flagged as a risk on Nov 21; it happened on the first night). The 2FA dialog times out
in ~5 min; the watchdog re-prompts after 2 h and then hourly, with pages, through the morning.

### 2.4 Box down again (power loss Sun 17:26)
Fifth power loss in 3 weeks (UPS decision D5 still open). It did not cost a touch this time only
because the weekend hold already had the gateway parked.

## 3. What worked
- Weekend hold: no pointless logins Sat → Sun; the IBKR Sunday reset did not cost an extra touch.
- Unattended path: no MessageBoxes, no stuck modal; the classifier read `token-rejected` correctly
  and cleared IBC before relaunching.
- Daily restart moved to 05:45 HKT and applied at the first login (`Auto restart time changed ...
  to 05:45 AM`); no router collision.
- Ledger + Monday report ran (the report said 0 touches because the week's touch had not happened).

## 4b. Addendum Thu 2026-11-26: what killed the gateway and the watchdog at Wed 16:41

**Cause: the Claude desktop app quit.** Both processes had been started from inside a Claude
session, so they belonged to the app's process tree and died with it.

Timeline, Wed 25 HKT. `%LOCALAPPDATA%\Claude\logs\main.log` is stamped in Windows local time
(EST); HKT = EST + 13.

| 16:50:09 | The keepalive task finds the watchdog dead and relaunches it via Task Scheduler. IBC is gone (`no-process`); new login and **touch at 16:53** |
| 19:23 | The Claude app starts again |

Why those two and nothing else:
- The watchdog was started by this session's shell (`Start-Process`, Tue 20:22) when it was
  restarted for F2–F4. IBC was started by that watchdog, so it was in the same process tree.
- Processes started by Task Scheduler survived: the API relay, the keepalive, and the Docker
  containers.
- No crash record, no PowerShell engine-stop event, no log line: what a forced tree kill looks like.
- The session ran no command between 16:41:13 and 16:53, so it did not kill anything itself.

Still exposed on Thu 26:
- The watchdog (pid 6524) was started from this session's shell at 21:08.
- The IBC java was started from the upgrade session's shell at Wed 23:46.
- **Quitting the Claude app kills the LIVE gateway (a YubiKey touch) and the watchdog.**

Fixes:
1. Restart the watchdog through `\IBKR\Quant Watchdog Keepalive`, never with `Start-Process` from a
   session. It then runs under Task Scheduler and so does every login it launches. This is free.
2. The gateway leaves the app's process tree at the next full login the watchdog launches: the
   Sunday weekly touch. Until then, don't quit the Claude app.
3. **Done Thu 26 ~21:30 HKT (user: "independent of Claude"): automatic hand-over.**
   - `Test-UnderClaude` (`ibkr-common.ps1`) is true when `claude.exe` is in the process's own
     Windows job or among its live ancestors.
   - `watchdog.ps1`, `ibkr-live-login.ps1` and `ibkr-live-autostart.ps1` check it first. If true,
     they start their on-demand task and exit: `\IBKR\Quant Watchdog Start`, `\IBKR\Live Login`
     (new, `setup-claude-independent-launchers.ps1`) or `\IBKR\Live Auto-Start`.
   - Loop brake: a second hand-over within 120 s is refused.
   - Verified: the check reads True in a Claude shell and False in a process started by Task
     Scheduler (temporary probe task, removed).
   - Not verified: the full self-relaunch of the watchdog and the login. That live test was blocked
     by the safety check because it starts a second watchdog and a login run.
   - The watchdog has run under Task Scheduler since 21:25 (pid 36576). Suite 58/58.
   - **Still exposed:** the IBC java started Wed 23:46 from a session shell. It moves out at the
     next full login (Sunday's weekly touch at the latest).
