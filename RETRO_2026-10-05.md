## The correction that mattered most

I concluded "no IBKR API yields the paper account's historical NAV" and wrote it into
`IBKR_HISTORY_SPEC.md` §0.1. **The user was right and I was wrong.** I had probed Flex with the
**live** query ID; a Flex query is scoped to the account it was created against, so it can only
ever return that account. I turned a per-query scoping property into a per-account
ineligibility claim — and did not test it, in a section whose own title promised not to assume.

Cost of the error: paper ran with 42 fewer days of real history than IBKR had been holding the
whole time. Now corrected in the spec, with the wrong table retained alongside the right answer
so the reasoning error stays visible.

## The near-miss worth remembering

Reconciling flows against IBKR, my first matcher demanded an **exact same-day, exact-amount**
match and flagged **3 of live's 6 real deposits** as contradicted — **+159,971.75 HKD** it
proposed to delete:

```
2026-07-08  +10,000.00   ibkr 2026-07-07 +10,000.00   -> "CONTRADICTED"
2026-07-10  +89,984.61   ibkr 2026-07-10 +90,000.00   -> "CONTRADICTED"
2026-08-11  +59,987.14   ibkr 2026-08-11 +60,000.00   -> "CONTRADICTED"
```

All six are real. IBKR stamps a transfer on its value date; the dashboard detects it from a cash
change, a day later and net of same-day activity. Loose the matcher to ±1 day / 2% and all six
corroborated.

Had that `--fix` run, live's P&L would have jumped ~160k of pure fiction. **The dry run is what
saved it** — and the reason I ran one despite having just been asked to treat IBKR as the
authority. Had I "trusted IBKR" and applied the fix directly, this would have been the worst
error of the session instead of the best near-miss.

## What I got right by not rushing

- Backfill **refuses** to overwrite recorded data, so re-running with a wider window twice could
  not damage what was already correct.
- Every NAV row stamped **end-of-day**, fixing B1 *before* using the tool rather than after
  producing spikes.
- Backups written before each `cash_flows` mutation (`cash_flows_pre_ibkr_reconcile_backup`).
- Kept the seeded-vs-independent distinction visible throughout, rather than quoting one blended
  agreement figure.

## What is still wrong

1. **The detector can recreate F1.** `detect_external_cash_flow()` still writes to `cash_flows`
   directly. Deleting the row stopped this instance, not the bug. Fix in
   `IBKR_REFERENCED_ACCOUNTING_SPEC.md` §3.1 — **not implemented**.
2. **Two doc corrections shipped without their code fix.** Both specs describe intended behaviour.
3. **October is unverifiable.** Flex stops at 09-30; `10-01..10-04` is dashboard-only, and the
   `2026-10-02` flow is *unjudgeable* rather than contradicted.
4. **Seed days remain circular.** 69 of paper's 101 days came from Flex itself — self-consistent,
   never independently confirmed. No second source exists for them.
5. **Last-sample-vs-close skew** is real (0.239% on paper vs 0.072% on live) and deliberately
   not fixed; it would cost intraday chart granularity.

## The one-line lesson

> I asserted an absence I had not tested, then nearly deleted 160k of real money while fixing it.
> Both errors came from the same place — treating a boundary in my own tooling as a fact about
> the world. **Probe the boundary; make the tool that could destroy data prove it first.**
